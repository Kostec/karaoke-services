# karaoke-services

Домашний сервис (docker-compose на Windows-ПК с GPU) для генерации караоке-песен UltraStar через UltraSinger из браузера, импорта готовых (usdb, zip, GitHub) и выкладки их в хранилища (Samba-шара Raspberry Pi, папки ПК, Яндекс Диск/WebDAV, Google Диск).
Два контейнера: `web` (FastAPI + статический фронт на ES-модулях без сборки) ставит задания в SQLite, `worker` (CUDA, UltraSinger, demucs, ffmpeg, yt-dlp + deno) их исполняет и выкладывает песню в встроенное «Локальное хранилище» и в основную цель (недоступную — докопирует позже). Интерфейс и все сообщения пользователю — на русском.

## Команды

Docker — только Linux-движок: `docker --context desktop-linux compose ...` или обёртка `./scripts/compose.ps1 ...` (PowerShell).
- Запуск/пересборка: `./scripts/compose.ps1 up -d --build`; веб — http://localhost:8090, API-доки — http://localhost:8090/api/docs.
- Проверка GPU и правок UltraSinger: `./scripts/compose.ps1 run --rm worker gpucheck` (успех — RC=0, последняя строка `gpucheck: OK …`).
- Только образ worker (15–30 мин с нуля): `./scripts/compose.ps1 build worker`.
- Логи: `./scripts/compose.ps1 logs --tail 100 worker` (или `web`).
- Python-тесты (pytest в Linux-контейнере): `docker --context desktop-linux compose --profile test run --rm tests` → 848 passed, 2 skipped (после смены зависимостей — `run --build`).
- Подмножество: `docker --context desktop-linux compose --profile test run --rm tests pytest -q tests/worker/test_runner_queue.py`.
- Фронт-тесты (Node 24, встроенный node:test): `node --test tests/frontend/` → 205 pass.
- Бэкап патча UltraSinger в `patches/karaoke-local.patch`: `./scripts/export-ultrasinger-patch.ps1` (читает `D:/Projects/UltraSinger`).
- CLI воркера внутри образа: `python -m karaoke_worker gpucheck|selfcheck|run`; entrypoint пропускает эти слова в CLI, прочее (`bash`, `python`) исполняет как есть.

## Архитектура

- web ↔ worker общаются только через SQLite `/data/karaoke.sqlite` (WAL, явные `BEGIN IMMEDIATE`) и файлы тома `data`; HTTP между ними нет.
- web: ставит задания (`Jobs.enqueue_with`), читает статус GPU из `settings[gpu_status]` (нет записи → `gpu.ok=null`), отдаёт лог из `/data/logs/<id>.log`, раз в 6 ч чистит корзину.
- worker: при старте `Settings.set_gpu_status(gpucheck.check())`, `Jobs.fail_interrupted()`, уборка `jobs/.new-*` старше часа и логов/входов старше `LOG_DAYS`; затем цикл `claim_next()` по одному заданию (8 ГБ VRAM). Без GPU берёт только `publish`, `import`, `video`, `copy` и `rename` (`needs_gpu=False`), GPU перепроверяет раз в минуту; при старте же удаляет `imports/*` старше часа.
- Отмена: web ставит `cancel_requested`, worker проверяет раз в секунду, убивает группу процессов (SIGTERM → 10 с → SIGKILL); `in/` сохраняется для «Перезапустить».
- Состояния: `queued → running → publishing → done|failed|cancelled`; `stage` — русское название этапа, на выкладке `STAGE_PUBLISH="publish"` (UI переводит). Упавшее на выкладке → `republish` создаёт задание `publish` с `source_job_id`.
- Поток generate: форма → `songs/<A>/<A - T>/jobs/.new-*` → rename в `jobs/<id>/in/` (`input.mp3`, `lyrics.txt`, `cover.<ext>`), `params.inputs` — пути от `DATA_DIR` → UltraSinger в `jobs/<id>/us|out` → `finalize` в `jobs/<id>/result` → `publish_song` (`Storage.upload_dir` в каждое хранилище выкладки) → `in/` копируется в `source/` (+`params.json`), обновляются Songs/Library, `jobs/<id>/` удаляется.
- Типы заданий: `generate`, `instrumental`, `import`, `publish`, `video`, `copy`, `rename`; `import` с `instrumental=true` делает минусовку один раз в `local`, в остальные хранилища выкладки её привозит `copy` с `replace=true, after_job=<instrumental>` (сбой постановки — только предупреждение в логе).
- Хранилища: список в `settings[targets]` (JSON, без встроенного `local`), основная цель — `settings[default_target]`; `song_id = sha1(target_id + rel_dir)` — у каждой копии песни свой id, строки `library` по `target_id`; задания песни (instrumental, video, правка нот, перегенерация с заменой — `params.target_id`, `api_jobs.replace_target_id`) работают в хранилище самой песни.
- Выкладка (`publish_song`): сначала `local` (сбой — задание падает), затем основная цель и при замене хранилище заменяемой песни; недоступная цель → задание `done` + `copy` с `wait=true` из `local`.
- Задание `copy`: params `{rel_dir, txt_name, from_target, to_target, replace, wait, replace_rel_dir?, after_job?}` + служебные `retry_at`, `wait_logged_at`; источник → `jobs/<id>/in/` (restart и ожидание не качают заново) → цель (есть и `replace=false` — пропуск; `replace` — старая в корзину цели, сбой — откат); при `wait` недоступная цель или незавершённое `after_job` → обратно `queued` с `retry_at` +60 с, этап «Ждёт хранилище «X»»/«Ждёт задание #N», лог не чаще раза в 10 мин; `replace_rel_dir` — прежняя папка в корзину цели; restart сбрасывает ожидание.
- Текст из LRCLIB: `GET /api/lyrics/search` → до 10 вариантов (`text`, `synced`); форма шлёт `lyrics_lrc` → `in/lyrics.lrc`, `params.inputs.lrc`, флаг `lrc_timing`; worker передаёт `--lyrics_timing` только при `lrc_matches` (иначе в лог `LRC_NOT_USED`); строка LRC с N метками = N строк, фронт строит чистый текст в том же порядке (`lrcPlainText`).
- Поток import: inspect → `imports/<token>/{files/…, meta.json}` (жизнь — час по mtime `meta.json`, потом 410) → `{token, source, songs[{index, artist, title, audio, cover, youtube, existing_song_id, warnings…}]}` → `POST /api/jobs/import` (`token, index, artist, title, audio? | youtube_url?, instrumental, replace`) копирует в `jobs/<id>/in/` (`song.txt`, `audio.<ext>` или `input.mp3`, `cover.<ext>`; обложку по `cover_url` качает веб) → worker: yt-dlp, если нет звука → `in/input.mp3` + `in/cover.jpg` (restart не качает заново) → ffmpeg mp3 → `.txt` без `#VIDEO/#BACKGROUND/#VIDEOGAP` → `finalize(**chosen_video)` (видео блока «Видео» возвращает свои `#VIDEO/#VIDEOGAP`) → `publish_song`; в `source/params.json` добавляются `source` (`usdb|files|url`) и `usdb_id`.
- usdb: учётка в `settings[usdb]` (`UsdbAccount`; PUT сохраняет только после успешного входа, пустой логин — удалить); без учётки → 400 `code=usdb_no_account`; неверный вход → 400 `field=password`, нет песни → 404, иначе 503.
- Замена песни (в каждом хранилище): та же папка — старая в корзину, выкладка, при сбое откат из корзины; другая папка — сначала выкладка, потом старая в корзину.
- Блок «Видео» generate/import: поля `video_mode` (`none|source|url|file|pack`), `video_url`, `video_file`, `video_height`, `videogap` → `params.video = {mode, url?, height, gap?}`, файл → `in/video.<ext>` и `params.inputs.video`; `source` у generate — ссылка звука, у import — `v=` из `#VIDEO`, иначе выбранная/первая ссылка звука; `pack` — видеофайл архива (meta.json `video_rel`), пустой `videogap` при `source/pack` берёт смещение из архива; inspect отдаёт у песни `video_links`, `video_file`, `videogap`. generate качает видео на шаге finalize (после UltraSinger); `in/video.*` в `source/` не копируется, в `source/params.json` — `video_url`.
- Задание `video` (`POST /api/jobs/video`, multipart `song_id, video(File)? | video_url? (+video_height), videogap?, remove?` — ровно один источник): ref `{artist, title, song_id}`, params `{rel_dir, txt_name, target_id, video_url?, video_height?, videogap?, remove?, inputs: {dir, video?}}` → `result/<основа .txt>.<ext>` (hardlink) → `publish_video`: в `.txt` меняются только `#VIDEO/#VIDEOGAP` (прежняя версия — в корзину), старый видеофайл с другим именем удаляется; `videogap` None — `#VIDEOGAP` не трогается, 0 — удаляется; restart не качает заново (`in/video.*`); такое же задание песни уже в очереди → 409.
- Замена песни (`publish_song`): если у старой было видео, а в новом `result/` своего нет — видео переносится под новое имя с `#VIDEO/#VIDEOGAP` (сбой — предупреждение в логе).
- instrumental: demucs `--two-stems vocals` → ffmpeg mp3 → `<аудио> [Instrumental].mp3` рядом с аудио, в `.txt` меняется только `#INSTRUMENTAL`.
- Раскладка тома data: `karaoke.sqlite`; `logs/<id>.log`; `songs/<A>/<A - T>/{source/,jobs/<id>/in/,debug/}`; `trash/<UTC>__<id>/{<A>/<A - T>/…, meta.json}` (без `meta.json` запись считается недописанной); `imports/<token>/{files/…, meta.json}` (токен `[A-Za-z0-9_-]{1,64}`, `DataPaths.import_dir`). Том `models` (`/models`) — кэши HF/torch/xdg/hyphen.
- Папка песни в хранилище: `<A>/<A - T>/<A - T>{.txt,.mp3, [Vocals].mp3, [Instrumental].mp3,.mid, [CO].jpg,.<видео>}`; БД: миграция V2 `library.video` → `LibraryItem.video` (в карточке песни), `SongEntry.video` — имя файла из `#VIDEO` или None; хранилища `kind=local` — папки контейнера: `/output` (= `LOCAL_OUTPUT_ROOT`, встроенное) или `/host/…` (= `HOST_FOLDERS_ROOT`); `OUTPUT_*` читаются только первой миграцией.
- REST: ответы JSON, ошибки `{"detail": "по-русски", "field"?}`; 422 переводится в 400; хранилище недоступно → 503; неверный Range → 416. Пароли API никогда не возвращает (`has_password`).
- Эндпоинты: `/api/status`, `/api/defaults` (+`max_import_mb`, `max_video_mb`, `video_heights`, `default_video_height`), `/api/jobs` (`generate`, `instrumental`, `import`, `video`, `copy`, `rename`, `{id}`, `cancel`, `restart`, `republish`, `log`, `log/stream`), `/api/import/inspect`, `/api/lyrics/search`, `/api/usdb/search` (по 50; без `language` — `Russian`, пустой — без фильтра), `/api/songs` (`?target=`, `rescan?target=`, `exists`, `{id}` с `source`, `lyrics`, `notes` GET/PUT, `audio` с Range, `cover`, `zip`, `details`, `file`, `tags` PUT, DELETE), `/api/tags`, `/api/trash` (+`restore`), `/api/targets` (+`test`, `default`, `browse`, `gdrive/*`), `/api/settings/output` (совместимость: основная цель в прежнем формате; новый фронт не зовёт), `/api/settings/usdb`, `/api/settings/yandex` (GET/PUT, `test`).
- `/api/targets`: GET → `{targets:[Target.public()], default_id, roots:{host: bool, output: true}}`; POST, `PUT /{id}` `{id?, name, kind: local|smb|webdav|yandex|gdrive, path, host, share, user, url, preset, client_id, password?}` → `Target.public()` (`gdrive` через POST → 400; «Папка ПК» = `/output` → 400); `DELETE /{id}` → `{ok}` (local 400, основная 409, нет 404); `PUT /default {id}`; `POST /test` → `{ok, label}`; `GET /browse?root=host|output&path=` → `{root, root_name, path, abs, parent, dirs}`; Google: `POST /gdrive/draft` → `{draft}`, `GET /gdrive/auth?draft=` → 302, `/gdrive/callback` → HTML (обмен кода, проверка, сохранение), `GET /gdrive/draft/{d}` → `{state: pending|connected|error, error?, target?}`.

- SSE лога: первым `event: start` с байтовым смещением, `id:` = смещение, в конце `event: end`; без `from` — последние 500 строк.
- GET `/api/songs/{id}/notes` → `{editable, reason?, bpm, gap, headers:[[k,v]], duet, singers:{p1, p2}, lines:[{break_beat, player?, notes:[{id, type, start, length, pitch, text}]}]}` (`player` 1/2 — только у дуэта, `singers` у соло — пустые строки); `id` ноты — её порядковый номер в файле (0…N-1), `break_beat` — разрыв после строки (у последней `null`).
- PUT тот же адрес `{gap, singers?, lines:[{break_beat, player?, notes:[{id|null, type, start, length, pitch, text}]}]}`: тайминги, высоты, типы, текст, новые (`id: null`) и удалённые (нет в теле) ноты, границы строк; `editable/reason/bpm/headers` игнорируются, прочие заголовки не меняются; `break_beat: null` у непоследней строки → конец её последней ноты; `gap` null или равен текущему → `#GAP` не трогается; дуэт пишется, если у какой-то строки с нотами `player=2` (иначе соло без `P`-меток и без `#P1/#P2/#DUETSINGERP*`), `player` — у всех строк или ни у одной; `break_beat` последней строки певца 1 не null → `- N` перед `P2`; имена перезаписываются, только если отличаются от прочитанных.
- PUT 400: нет нот, неизвестный тип, начало < 0, длина < 1 (ноту длины 0 тоже отклоняет), высота вне −40…100, перевод строки в слоге, перекрытие, разрыв не между строками, чужой/повторный `id`, `gap` < 0, у дуэта — нет/неверный `player` строки (ошибки «Певец N, строка K: …», K — внутри партии); 409: певцы `P3`+, `#RELATIVE`, нет `#BPM` (GET тогда `editable:false` + `reason`), сбой корзины. Изменился файл → старая версия в корзину, `write_atomic`; ответ — карточка песни.

- «Переименовать»: `POST /api/jobs/rename` `{song_id, artist, title}` (`api_jobs.rename`) → 201 `{jobs:[{job_id, target_id, song_id}]}` — задание `rename` на каждую копию (`Library.copies`, хранилища из настроек; `song_id` — новый id копии `song_id_for(target_id, new_rel_dir)`); 400 пустое поле (`field`) / «Имя не изменилось» (тот же `naming.song_dir`; смена регистра — можно), 404, 409 `RENAME_BUSY` — `_song_busy`: активное задание `BUSY_TYPES` (`Jobs.active`) любой копии по `song_id`/`match_key`, у `rename` — ещё по новому имени и `rel_dir/new_rel_dir` из params; 409 `field=title` — `_rename_conflict`: другая папка `new_rel_dir` (без регистра) в индексе любого хранилища или своя другая песня (`Songs.by_rel_dir_folded`, папка `songs/<new_rel>/source`). params `{rel_dir, txt_name, target_id, artist, title, new_rel_dir, new_txt_name, wait: true}` + `retry_at/wait_logged_at`; restart их снимает (такое же активное — 409).
- `RenameHandler` (`handlers.py`): `download_song_dir` (общий с `CopyHandler`; restart берёт вход родителя) → `result/` по `naming.rename_plan(names, old_bases, new_base, fallback=)` (прежние основы — `naming.rename_bases`: имя папки и `base_name` из ref задания, запасная — стем `txt_name` вроде `song`; хвост после основы — с `.`/пробела, `A - T (duet).txt` → `B - U (duet).txt`; имя `.txt` результата — из плана, `new_txt_name` веба — `naming.renamed_txt_name` по тому же правилу; сбой диска — `JobFailed("prepare")`; два файла в одно имя без регистра — `JobFailed` до записи; жёсткие ссылки) и `rename_txt` (`#ARTIST/#TITLE` + `RENAME_FILE_HEADERS`, без регистра; не кодируется → `JobFailed("input")`) → в `new_rel_dir` уже `.txt` байт в байт как наш — своя недописанная выкладка (restart после падения): шаги доводятся без выкладки; другая `new_rel_dir` — `JobFailed("conflict", «Песня «А — Т» уже есть в «X»»)`; иначе в params ставится `upload_started: <new_rel_dir>` (наследуется при restart) и `_publish` (сбой — недописанная `new_rel_dir` удаляется; не удалилась — `new_rel_dir` без песни при своей метке `upload_started` удаляется следующей попыткой; обрыв при `wait` — ожидание), потом старая в корзину, если её `.txt` ещё на месте (`RENAME_REASON` «переименована», сбой — предупреждение); отличие только регистром — сначала корзина (старой уже нет — сразу выкладка из `in/`; сбой корзины при живом хранилище — `JobFailed("trash")`, не ожидание), при сбое откат. Недоступно — `wait_retry` («Ждёт хранилище «X»», общий с `copy`). После: индекс (старая строка убрана), `Songs.rename(id, rel_dir=, artist=, title=)` + перенос `source/` (один раз; папка назначения занята — не трогается, предупреждение), `Tags.copy_key(old, new)` (без дублей; `JobContext.tags`), `Tags.drop_key(old)` — только когда в индексе не осталось копий со старым `match_key`, пустые папки тома data — `_prune_song_dir`.
- Фронт: «Переименовать…» в `songMenuItems` → `openRenameDialog(song, env)` (`song-actions.js`: ошибки у поля по `field`, Enter — отправка, `watchJob` на каждое задание; `env.afterRename(newId)` страницы песни — `location.replace('#song?id=…')`); чистая логика — `rename-logic.js` (`renameErrors`, `renameBody`, `ownRename`), `api.renameSong`; «Очередь» — подписи «Копирование»/«Переименование». Тесты: `tests/worker/test_runner_rename.py`, `tests/api/test_rename.py`, `tests/frontend/rename-logic.test.mjs`.

## Подводные камни

- У Docker Desktop активен Windows-движок — всегда `--context desktop-linux` (или `scripts/compose.ps1`); движок не переключать.
- Сеть контейнеров: `dns: 77.88.8.8, 1.1.1.1` и выключенный IPv6 (`sysctls`) в `docker-compose.yml` — DNS Docker Desktop сбоил, а AAAA-адреса без маршрута ломали Яндекс/LRCLIB; yt-dlp везде с `-4`.
- Шара на Pi не даёт переименовать поверх существующего файла (Samba на exFAT/NTFS-диске → «нет доступа»): `Storage.write_atomic` при отказе меняет файл в три шага (`_swap`: старый → `.old-*`, новый на место, старый удалить; сбой — откат), а «нет доступа»/sharing violation ещё и ждёт повторами (`BUSY_RETRY_DELAYS`).
- Имена `pi`/`pi.local` в контейнерах не резолвятся — в адресе SMB-хранилища (и `OUTPUT_SMB_HOST`) только IP.
- Порт 8080 на хосте занят jenkins — `WEB_PORT=8090` (внутри контейнера веб слушает 8080).
- Linux-колёса torch cu126 собраны без sm_61: на Pascal исполняется sm_60 — это норма (`gpucheck.runnable_arch`); cu128 без Pascal вовсе, сборку валит `worker/build/check_torch_arch.py`.
- Зависимости UltraSinger фиксируются по его `uv.lock` (`worker/build/lock_constraints.py` → `/etc/uv-constraints.txt`), наши пины важнее (torch/torchaudio/torchvision cu126, `numpy<2.5`); без этого swift-f0 0.3.0 ломает сигнатуру SwiftF0 (ловит `selfcheck`).
- GTX 1080 не умеет float16 — compute type только `int8`.
- Тесты — только в Linux-контейнере: воркер использует POSIX-группы процессов; на Windows-хосте pytest не запускать.
- После изменения зависимостей (pyproject, Dockerfile) — `run --build`, иначе образ tests старый; исходники монтируются в `/app` editable.
- `.gitattributes` `* text=auto eol=lf`: Dockerfile/sh/py идут в Linux-контейнеры; фикстуры тестов — binary.
- Форк `D:/Projects/UltraSinger` (ветка `karaoke-local`, remote `fork`) правится только с явного разрешения пользователя в текущей задаче; после правки — коммит в `karaoke-local`, `./scripts/export-ultrasinger-patch.ps1`, `git -C D:/Projects/UltraSinger push fork karaoke-local` — только с согласия (образ worker собирается из `ULTRASINGER_GIT`); проверка — `gpucheck`.
- Сборка worker падает на `RUN python -m karaoke_worker selfcheck`, если rebase форка потерял правку (флаги `--lyrics/--vad_onset/--vad_offset/--lyrics_timing`, `lyrics_alignment`, `midi_creator`, SwiftF0).
- yt-dlp не фиксируется по `uv.lock` (`lock_constraints.FRESH`) и ставится последним слоем образа: старая версия получает от YouTube HTTP 403. Обновить только его: `./scripts/compose.ps1 build --build-arg YTDLP_REFRESH=<дата> worker`, затем `./scripts/compose.ps1 up -d worker`.
- yt-dlp без `deno` (в образе — `denoland/deno:bin-2.5.6`) получает с YouTube не все форматы; `selfcheck` проверяет оба.
- Миграция `output → targets` меняет `song_id` всех песен (id = sha1(target_id + rel_dir)), старые `target_id` заданий/корзины понимает `resolve_target_id`; удалённое хранилище → `StorageError` «хранилище удалено из настроек».
- Вход в Google: `redirect_uri` строится из адреса запроса (`/api/targets/gdrive/callback`), Google принимает http только для localhost — веб для этого открывать через http://localhost:8090 (подсказка `needsLocalHint`).
- Тома переживают `compose down`; `compose down -v` удаляет БД и корзину.
- Формат UltraSinger: пробел-граница слова стоит в конце слога, «~» — продолжение гласной (бывает с пробелом с любой стороны); `lineText`/`joinNext`/`setLineText` в `notes-model.js` это учитывают — не «чинить» пробелы при правке.
- Сдвиг ноты левее бита 0 (move, resize, addNote, retime) не ошибка: модель сдвигает всю песню вправо и уменьшает `gap` (`settle`); ошибка только при `#GAP` < 0. Предпросмотр перетаскивания пересчитывает биты через `rebaseBeat`.
- Код web и worker запечён в образы (исходники монтируются только у `tests`): после правок Python или фронта — `./scripts/compose.ps1 up -d --build web worker`, иначе работает старый код; в браузере ES-модули кэшируются — жёсткая перезагрузка (Ctrl+F5).
- curl из Git Bash портит кириллицу в аргументах — тестовые данные с русским текстом слать из браузера или из UTF-8 файла (`--data-binary @file`).
- `ImportHandler` всегда снимает `#VIDEO/#BACKGROUND/#VIDEOGAP` из `.txt` пакета; видео возвращает только `finalize` по выбору блока «Видео» (`chosen_video`); сбой скачивания видео задание не валит.
- Общий `state.notes` дуэта — слияние партий по времени, порядок осмыслен только внутри партии: живая нота — `noteAt(voiceNotes(state, v), beat)` по каждому певцу, индексы перетаскивания слога — из `voiceNotes`, подсветка строки — `lineAt(lines, beat, v)`.
- Свои теги держатся за ключ «исполнитель — название» (`song_tag_key`), а не за папку: «Переименовать…» их переносит (`RenameHandler._rename_tags`: `Tags.copy_key` на новый ключ, `drop_key` старого — только когда в индексе не осталось копий со старым ключом), а ручная правка `#ARTIST/#TITLE` вне сервиса — нет (после rescan теги остаются на старом ключе без песни).
- Браузер не проигрывает видео `.avi` (и часть `.mkv/.mpg`): страница песни проверяет `canPlayType` по расширению (`song-page-logic.browserCanPlay`) и вместо плеера пишет «Браузер не умеет воспроизводить формат .X» со ссылкой «Скачать»; сбой уже начатого плеера — «Не удалось воспроизвести…» с той же ссылкой.
- `GET /api/songs/{id}/file` отдаёт только файлы верхнего уровня папки песни (подпапки — 404).
- Шара отдаёт 503 при параллельном чтении одного файла (`<audio>` и волна одновременно) — `loadPeaks` повторяет до 3 раз через 1,5 с.

## Как здесь работает Autopilot

Сборка ведётся навыком `/autopilot`. Требования, спецификация и таски — в `.autopilot/`.
Прогресс — `.autopilot/dashboard.html`. Требование из `manifest.md` может снять
только пользователь. Прерванную сборку продолжает «продолжи автопилот».

### Правка без автопилота

Мелкий баг или доводка после сборки — обычная сессия, без прогона.

Сначала прочитай:
1. `.autopilot/PROGRESS.md` — что не доделано, известные баги, о чём договорились с пользователем.
2. Что правили после последней сборки — первая строка таблицы в «История git».
3. Только если правка их касается: почему сделано так — `docs/adr/`; что именно просили — `manifest.md` в папке сборки (указана в начале `PROGRESS.md`).

После правки:
- коммит — по правилам из «История git»;
- строка в «Правки без автопилота» в `PROGRESS.md`: дата — что — почему;
- починенный пункт из «Не доделано» или «Известные баги» — удали;
- договорились с пользователем о том, что следующая сборка не должна пересматривать, — строка в «Договорились», его словами.

### История git

Целиком не читай — бери срез под вопрос:

| Вопрос | Команда |
|---|---|
| что правили после последней сборки | `git log --oneline "$(git log -1 --format=%h --grep='^Autopilot: сборка сдана')"..HEAD -- . ':(exclude).autopilot'` |
| всё, что делали ради требования | `git log --oneline --grep="R02"` |
| история файла | `git log --oneline -10 -- <файл>` |
| когда появился или исчез код | `git log --oneline -S "<фрагмент>"` |
| почему строка такая | `git blame -L <с>,<по> <файл>`, затем `git show <sha>` |
| что внутри коммита | `git show --stat <sha>` |

Срез длиннее ~30 коммитов — отдай его субагенту и возьми выжимку в десять строк.

Коммит: заголовок — что (`fix: даты в одном формате`), тело — почему, трейлер
`--trailer "Requirements: R02"`, если правка касается требования из `manifest.md`.
