# 0023. Хранилище определяется стабильным id `t_…`, а не адресом

## Контекст

Песни, задания и корзина ссылались на папку результата через `target_id`, собранный из адреса (`smb://…`, `local:/output…`); с появлением нескольких хранилищ правка адреса или логина рвала бы все ссылки на него.

## Решение

Каждое хранилище — запись списка `settings[targets]` с коротким id `t_<8 hex>`, который выдаётся при создании и не меняется при правке; адрес, логин и путь — свойства записи. Встроенное локальное хранилище имеет постоянный id `local`, всегда первое, не удаляется и не правится. Основная цель — отдельный ключ `default_target`. Миграция переводит старую цель в хранилище и переписывает `target_id` строк `library` и записей корзины в той же транзакции; `song_id`, как и раньше, считается от id хранилища и `rel_dir`, поэтому после миграции он у всех песен новый.

## Почему

- **Оставить адрес ключом** отвергнуто: смена IP шары или пароля превращала бы хранилище в новое, индекс и корзина теряли бы свои песни — ровно та потеря настроек при переключении, на которую жаловался пользователь.
- **Сохранить старые `song_id` таблицей соответствия** отвергнуто: второй вид id пришлось бы поддерживать во всех эндпоинтах ради ссылок, которые живут только в адресной строке и в истории заданий.
- **Хранить локальное хранилище обычной записью `t_…`** отвергнуто: на `local` завязана выкладка «всегда локально» (ADR 0024), и оно должно существовать при любом состоянии настроек.

## Последствия

- Старые ссылки `#songs/<id>` и `ref.song_id` заданий, поставленных до обновления, больше не указывают на песню — принято сознательно.
- `jobs.params.target_id` старого формата сопоставляется с новым id при чтении: правило миграции живёт в коде, пока в истории есть такие задания.
- Удалённое из настроек хранилище оставляет в корзине записи с id, которому ничего не соответствует, — `restore` отвечает 409.
- Откат на прежнюю схему потребует обратной миграции индекса и корзины.
