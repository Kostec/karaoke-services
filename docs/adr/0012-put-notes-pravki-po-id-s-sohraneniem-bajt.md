# 0012. PUT notes принимает любые правки нот и сопоставляет их по `id`

## Контекст

Редактор нот должен менять тайминги, длительности, высоты, типы, добавлять и удалять ноты, а прежний `PUT /api/songs/{id}/notes` разрешал менять только текст слогов и границы строк. Файлы `.txt` приходят из UltraSinger, usdb и чужих архивов в разных кодировках, с BOM, CRLF и строками, которые разборщик не понимает.

## Решение

`GET /notes` отдаёт у каждой ноты `id` — её порядковый номер в исходном файле (0…N-1). `PUT /notes` принимает полный список строк с нотами: уцелевшие ноты опознаются по `id`, новые приходят с `id: null`, отсутствующие считаются удалёнными, плюс `gap`. Неизменённые ноты и все прочие строки файла пишутся байт в байт; изменённые и новые — в каноническом виде с переводом строки файла, с сохранением кодировки и BOM. Неразобранные строки тела остаются перед той нотой, перед которой стояли (если она удалена — перед следующей уцелевшей), всё после `E` — как было. `#GAP` переписывается только при смене `gap`, прочие заголовки не трогаются. Без правок файл не переписывается. Сервер проверяет то же, что клиент: типы, диапазоны, порядок без перекрытий, биты разрыва, существование и уникальность `id`, `gap ≥ 0`; дуэт, `#RELATIVE` и отсутствие `#BPM` — 409.

## Почему

- **Перезаписывать весь файл из модели клиента** отвергнуто: пропали бы неразобранные строки, комментарии, исходное форматирование чисел и переводы строк, а каждое сохранение давало бы огромный дифф в корзине и могло сломать файл, который другие программы читали нормально.
- **Отправлять список операций (переместить, удалить, вставить)** отвергнуто: сервер должен был бы повторить всю логику модели редактора, и любое расхождение операций между JS и Python портило бы песню. Полное состояние с `id` проверяется проще и одинаково с обеих сторон.
- **Сопоставлять ноты по позиции или по времени** отвергнуто: после удаления, вставки или перетаскивания позиция и время перестают однозначно указывать на исходную строку файла.
- **Сохранить старый запрет на тайминги и сделать отдельный эндпоинт** отвергнуто: две разные записи одного файла с разными правилами — лишний шов, а прежний редактор строк всё равно удаляется.

## Последствия

- `id` действителен только для той версии файла, с которой открыт редактор. Если файл поменялся снаружи между GET и PUT, правки лягут не на те ноты; защиты от одновременной правки нет.
- Изменённая нота теряет своё исходное написание (лишние пробелы, формат чисел) — она пишется канонически. Файл получается смешанным: часть строк как была, часть в нашем формате.
- Правила проверки продублированы в `notes-model.js` и `web/app/notes.py`; менять их нужно синхронно, иначе клиент пропустит то, что отвергнет сервер, или наоборот.
- Дуэты и `#RELATIVE` по-прежнему только для просмотра; их поддержка потребует расширить формат `id` и сопоставление голосов.
