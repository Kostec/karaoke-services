# 0036. Резервная копия настроек не содержит секретов; пароль не переходит на сменённый адрес

## Контекст

Нужен один файл с тегами, хранилищами, основной целью, логином usdb, зеркалами и настройками Telegram. Файл пользователь будет хранить и переносить, в том числе на другую установку.

## Решение

Выгружаются только поля из явного списка (`TARGET_FIELDS` и аналоги); секретные поля туда не попадают по построению, тест проверяет отсутствие `secret/token/password` в выгрузке. Загрузка идёт в два шага: предпросмотр (`apply=0`), потом применение. Ничего не удаляется: теги сопоставляются по имени, хранилища — по `id`. Хранилища, которым нужен пароль или вход в Google, перечислены. Если у существующего хранилища в файле другой адрес, прежний пароль на новый адрес не переносится.

## Почему

- **Выгрузка паролей, пусть и зашифрованных** отвергнута: придётся придумывать и хранить ключ, а файл с настройками лежит в обычных папках и облаках. Пользователь прямо сказал «без паролей».
- **Исключать секреты чёрным списком** отвергнуто: новое секретное поле в `Target` попало бы в файл молча. Белый список падает безопасно — новое поле просто не выгружается.
- **Оставлять прежний пароль при смене адреса** отвергнуто: файл с чужим адресом отправил бы сохранённый пароль на чужой сервер.
- **Полное восстановление с заменой настроек** отвергнуто: удаление хранилищ и тегов по файлу необратимо.

## Последствия

- После восстановления на чистой установке каждое хранилище с паролем настраивают заново.
- Токен Яндекс Музыки не переносится вообще.
- Новое поле настроек не попадёт в копию, пока его не внесут в список вручную.
- Откатить настройки к файлу нельзя: загрузка только добавляет и обновляет.
