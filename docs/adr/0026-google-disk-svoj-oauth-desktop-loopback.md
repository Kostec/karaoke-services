# 0026. Google Диск — через собственный OAuth-клиент Desktop пользователя с loopback-возвратом

## Контекст

Нужно сетевое подключение к Google Диску; без OAuth у Диска сетевого доступа нет, а у домашнего сервиса нет публичного адреса.

## Решение

Пользователь создаёт в Google Cloud Console свой OAuth-клиент типа Desktop и вводит в «Настройках» Client ID и Client secret. «Войти через Google» ведёт на `accounts.google.com` с `redirect_uri = <origin веба>/api/targets/gdrive/callback`, scope `drive`, `access_type=offline`, `prompt=consent`; черновик хранилища живёт в памяти веба 10 минут, callback меняет code на токены, проверяет папку и сохраняет хранилище с refresh-токеном. `GDriveStorage` работает с Drive REST v3 через `Http`, access-токен обновляет по refresh-токену и в БД не пишет.

## Почему

- **Встроенный client_id проекта или чужой (например, rclone)** отвергнут: секрет оказался бы в репозитории, а чужой клиент живёт под чужими квотами и может быть отозван владельцем.
- **Папка Google Drive для ПК, примонтированная в контейнер**, отвергнута: пользователь потребовал сетевое подключение, а клиент Google синхронизирует по-своему.
- **rclone** отвергнут по тем же причинам, что для Яндекса (ADR 0025), и своего OAuth-клиента он всё равно не отменяет.
- **Web-клиент с публичным redirect** отвергнут: у сервиса нет публичного HTTPS-адреса, а loopback Google разрешает только Desktop-клиентам.
- **Scope `drive.file`** отвергнут: он не видит уже существующие на Диске папки и песни.

## Последствия

- Вход работает только из браузера на том же ПК (`localhost`/`127.0.0.1`); с телефона — подсказка подключать с компьютера.
- Без собственного OAuth-клиента тип недоступен: нужен аккаунт Google Cloud и разовая настройка.
- Scope `drive` даёт сервису доступ ко всему Диску, а не только к папке песен.
- Клиент в статусе «Testing» у Google получает refresh-токены с ограниченным сроком — тогда вход придётся повторять.
- Черновик в памяти веба теряется при перезапуске контейнера посреди входа.
