# 0032. Проверка библиотеки и зеркало — задания воркера; отчёт лежит файлом в томе data

## Контекст

Обе операции обходят хранилища целиком, включая SMB на Pi; при тысячах песен это минуты. Web отвечает на запросы и не должен зависеть от медленной шары.

## Решение

`libcheck` и `mirror` — типы заданий без GPU, исполняются воркером; виден процент и текущее хранилище. Результат проверки пишется в `reports/libcheck.json` через `DataPaths`, итог прогона зеркала — в `last_result` настройки зеркала. Зеркало запускается раз в `MIRROR_EVERY_S = 1800` на каждое включённое зеркало без активного `mirror` и по кнопке.

## Почему

- **Обход в процессе web** отвергнут: долгий запрос к шаре держит обработчик, нужен отменяемый процесс, а у воркера уже есть очередь, отмена и лог.
- **Хранить отчёт в SQLite** отвергнуто: отчёт — один большой документ, который целиком перезаписывается и читается; таблица находок с миграцией ради него избыточна, а файл можно открыть руками.
- **Планировщик внутри web** отвергнут: web и worker общаются только через БД и файлы, а зеркало всё равно исполняет воркер.

## Последствия

- Проверка и зеркало стоят в той же очереди, что и генерация, и ждут своей очереди; долгая генерация задерживает проверку.
- Без запущенного воркера зеркало молчит, а по кнопке задание просто стоит в `queued`.
- Отчёт один: новая проверка стирает прошлый, истории нет.
- Правило «у зеркала есть активное задание» должно быть одним в core, иначе web, restart и воркер разойдутся (найдено ревью, F1).
