# 0013. Сдвиг нот левее бита 0 меняет `#GAP`

## Контекст

UltraSinger ставит первую ноту песни на бит 0, а время бита 0 задаёт `#GAP` в миллисекундах. Пользователь просил «выделить всё» и сдвигать всю песню по времени (G02), в том числе раньше; отрицательный бит в `.txt` караоке-программы понимают по-разному.

## Решение

Если правка уводит ноту левее бита 0 — перетаскивание, растяжение за левый край, новая нота, отстукивание, — все ноты сдвигаются так, чтобы самая ранняя встала на бит 0, а `gap` уменьшается на столько же миллисекунд (`бит × 60000 / (BPM × 4)`). Время звучания нот, которые не двигали, не меняется. `gap` меньше 0 не допускается: «Раньше начала трека сдвигать некуда: #GAP не может быть меньше 0». `#GAP` пишется целым числом и только когда `gap` изменился.

## Почему

- **Разрешить отрицательные биты** отвергнуто: формат UltraStar их не гарантирует, часть программ их отбрасывает или ломается.
- **Запретить сдвиг раньше бита 0** отвергнуто: у сгенерированных песен первая нота уже на бите 0, и сдвинуть песню раньше было бы невозможно — а это частая доводка, ради которой и просили G02.
- **Применять правило только к «выделить всё»** было в исходном плане и уточнено при сборке: любая правка левее бита 0 упирается в ту же проблему, а отдельное поведение для частного случая путало бы.
- **Менять `#GAP` прямым вводом** отвергнуто: правка заголовков вне рамок, а через сдвиг нот пользователь видит результат на таймлайне и слышит его.

## Последствия

- Одна правка одной ноты может переписать начала всех остальных нот в файле: с точки зрения сохранения байт (ADR 0012) изменёнными становятся почти все строки тела.
- При дробном результате `gap` округляется до целого при записи, поэтому время звучания сохраняется с точностью до миллисекунды, а не точно.
- Правило живёт в модели клиента; сервер только проверяет `gap ≥ 0` и порядок нот и сам ничего не сдвигает.
- Если песня позже будет переразмечена другим `#BPM`, пересчёт `gap` через формулу бита придётся повторить — правка `#BPM` сейчас вне рамок.
