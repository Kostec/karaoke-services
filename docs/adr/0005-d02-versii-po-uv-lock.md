# 0005. D02: версии зависимостей UltraSinger берутся из его uv.lock

## Контекст

План предполагал, что зависимости UltraSinger в образе worker достаточно поставить по диапазонам из `pyproject.toml` через `uv pip`, а потом поверх поставить наши torch cu126 и `numpy<2.5`.

## Решение

Реальная генерация на GPU упала на этапе «Определение высоты нот». С PyPI приехал `swift-f0` 0.3.0 с другим API: `SwiftF0(fmin=…)` бросает `TypeError`. Поэтому версии всех зависимостей UltraSinger закрепляются по его `uv.lock`. Исключения — torch, torchaudio, torchvision и numpy: их задаём мы. При сборке проверяется сигнатура `SwiftF0`.

## Почему

- **Ставить по диапазонам из `pyproject.toml`** отвергнуто: доказано, что это ломает генерацию. Любой релиз зависимости на PyPI может сломать сборку, которая вчера работала.
- **Закрепить вручную только `swift-f0`** отвергнуто. Это лечит один симптом, а несовместимость может прийти из любой другой из десятков зависимостей. Lock-файл upstream — единственный набор версий, который авторы UltraSinger действительно проверили.
- **`uv sync` по lock-файлу целиком** отвергнуто. Lock тянет torch с индекса cu128 без Pascal (см. ADR 0003 и ADR 0004), а обойти это без правки lock в форке нельзя.
- **Свой requirements.txt в нашем репозитории** отвергнут: он рассинхронизируется с upstream при каждом rebase, и обновлять его пришлось бы руками.

## Последствия

- Сборка воспроизводима, пока не меняется `uv.lock` в ветке `karaoke-local`. После rebase на новый upstream версии меняются вместе с lock, и это надо проверять реальной генерацией, а не только `gpucheck`.
- Наш torch cu126 и `numpy<2.5` расходятся с тем, что зафиксировано в lock. Совместимость этой пары с остальными закреплёнными пакетами — на нас, и lock её не гарантирует.
- В Dockerfile появляется шаг, который переводит lock в список закреплённых версий с исключениями. Если формат `uv.lock` изменится, этот шаг сломается.
- Самопроверку сигнатуры `SwiftF0` придётся убрать или поправить, если upstream сам перейдёт на новый API.
