## 1. Страница песни (фронт)

Файлы в `web/static/js/`: `song-page.js` (260 строк), `song-page-logic.js` (чистая логика), `song-actions.js`, `player.js`, `songs.js`, `menu.js`, `tags-ui.js`.

**Жизненный цикл `song-page.js`.** Модульные переменные: `root, songId, seq, fromList, lastFrom, trashDays, renamed`. `mount(section)` запоминает `root`. `show(params)` берёт `id` из `#song?id=`, зовёт `load()` и `getDefaults()` (для `trashDays`). `hide()` делает `pausePlayers(); closeMenu(); songId=''`.

`load({quiet})` увеличивает `seq` и параллельно запрашивает `api.songDetails(id)`, `api.tags()` и `api.targets()`. Ответы с устаревшим `seq` или `songId` отбрасываются. Затем идёт `render(details, tags, targetsRes)`. При ошибке: если `quiet` и статус не 404, прежний вид остаётся; иначе показывается `notFound()` или `unavailable(e)` с кнопкой «Повторить».

**Что вызывает полную перерисовку.** Это `reload()` (внизу файла): `if (root && !root.hidden && songId) load({quiet:true})`. Его кладут в `env.reload`. Он вызывается из:
- `openSongTagsDialog` → `openTagsDialog(song, {onSaved: () => env.reload?.()})` после «Теги сохранены»;
- `openCopyDialog` после постановки: `env.reload?.()` (чтобы появилась метка «ждёт копирования»);
- `watchJob(job, () => env.reload?.())` в `makeInstrumental`, `openVideoDialog.send`, `openRenameDialog`;
- `removeSong` (`afterRemove` → `location.hash = '#songs'`);
- кнопки редакторов: `ed.open(song, {reload: env.reload})`, редактор вызывает `reload` после сохранения.

`watchJob(job, onFinal)` (в `song-actions.js`) опрашивает `api.job(id)` каждые `WATCH_MS = 3000` мс, пока состояние не станет `JOB_FINAL` (`done|failed|cancelled`). Модульный `Set watched` не даёт завести дубль. 404 задания прекращает слежение.

**`render()` строит всё заново.** Он собирает `hero`, `mediaCard`, `lyricsCard`, `infoCard`, `storeCard`. Перед заменой вызывается `pausePlayers()`, затем `clear(root).append(backLink(), hero, h('div',{class:'song-grid'},...))`. Отсюда два известных бага из PROGRESS.md:
- играющий плеер останавливается (`pausePlayers()` прямо в `render`);

После перерисовки старые элементы остаются в `players`, пока что-нибудь не заиграет. Правильное исправление: в `player.js` добавить `releasePlayers()` (pause + `removeAttribute('src')` + `load()` + `players.clear()`), звать при замене DOM и в `hide()`, либо обновлять только изменившиеся блоки (`song-grid` собирается из четырёх независимых карточек, их можно пересобирать по отдельности).

## 2. Теги

`core/karaoke_core/db.py`, классы `Tag` (стр. ~1034), `Tags` (~1048), `TagError(message, field)` (~1015). Константы: `TAG_COLORS = ("blue","violet","pink","orange","yellow","teal","gray","red")`, `DEFAULT_TAG_COLOR = "blue"`, `TAG_NAME_MAX = 40`, `_SQL_CHUNK = 500`. Схема V4: `tags(id TEXT PK, name, name_key TEXT UNIQUE, color, created_at)`, `song_tags(song_key, tag_id, PRIMARY KEY(song_key, tag_id))` + индекс `song_tags_tag`.

Методы `Tags(conn)`:
- `_check_name(name)` (static): `" ".join(split())`; пусто → `TagError("Введите название тега","name")`; длиннее 40 → `"Не длиннее 40 символов"`.
- `_check_color(color)` (static): `color not in TAG_COLORS` → `TagError("Неизвестный цвет","color")`. `None` и `''` не входят в палитру, поэтому отказ.
- `_check_unique(key, except_id=None)`: `SELECT id FROM tags WHERE name_key=?`; чужой id → `TagError("Такой тег уже есть","name")`.
- `create(name, color=DEFAULT_TAG_COLOR) -> Tag`: id `uuid4().hex`; `_check_unique` выполняется внутри `with _tx(self.conn)` (то есть `BEGIN IMMEDIATE`), потом `INSERT`.
- `update(id, *, name=None, color=None)`: внутри `_tx`; `None` — не менять; неизвестный id → `KeyError`; затем `_check_unique(key, except_id=id)`.
- `delete(id) -> int` (снятых связей), `for_songs(keys) -> {song_key: [tag_id]}`, `set_for_song(key, tag_ids)` (полная замена набора, неизвестный id → `KeyError`), `counts() -> {tag_id: n}`, `copy_key(old, new)` и `drop_key(key)` (см. п. 13).
- `_tx(conn)` (db.py ~162): `BEGIN IMMEDIATE` / `ROLLBACK` при исключении / `COMMIT`; соединение с `isolation_level=None`, `busy_timeout=30000`.

**Пустой `color` (баг PROGRESS).** `web/app/api_tags.py`: `class TagIn(BaseModel): name: str = ""; color: str | None = None`. `create_tag` делает `ctx_of(request).tags.create(body.name, body.color or DEFAULT_TAG_COLOR)`. Так `None`, `""`, отсутствие поля превращаются в синий. Для «пустой color → 400 `{detail:"Неизвестный цвет", field:"color"}`» нужно различать «поле не передано» (по контракту фронта `api.createTag({name,color})` всегда шлёт цвет из `colorPicker`) и `""`. Проще: в `create_tag` вызывать `tags.create(body.name, body.color)` с `color: str | None = None` и считать `None`/`""` ошибкой. Либо оставить умолчание только для отсутствующего поля, а `""` отклонять. Решить в тикете. `PUT /tags/{id}` (`TagPatch`): `color=""` сейчас → 400 «Неизвестный цвет» (проходит в `update` как не-`None`), а `name=""` → «Введите название тега».

**Гонка двух одновременных создателей.** По коду `_check_unique` и `INSERT` уже внутри одной `BEGIN IMMEDIATE`-транзакции, соединения у web потоковые (`AppContext.conn()` через `threading.local`, `check_same_thread=False`), `UNIQUE(name_key)` стоит в схеме. Второй поток ждёт блокировку до 30 с и затем получает `TagError`. Воспроизвести тестом с двумя потоками (разные `db.connect(...)` к одному файлу) до правки; если 500 всё же возможен, это `sqlite3.IntegrityError`/`OperationalError("database is locked")` — ловить и превращать в `TagError("Такой тег уже есть","name")` внутри `create`/`update`.

## 3. Library.copies и схема library

`core/karaoke_core/db.py`, схема V1: `library(target_id, rel_dir, txt_name, artist, title, audio, instrumental, cover, is_duet, own_song_id, mtime REAL, scanned_at, PRIMARY KEY (target_id, rel_dir))`; V2: `video TEXT`; V3: `song_id TEXT` + `CREATE INDEX library_song_id ON library(song_id)` (с бэкфилом `UPDATE library SET song_id = karaoke_song_id(target_id, rel_dir)`, где `karaoke_song_id` — SQL-функция, зарегистрированная в `connect()` до `_migrate`). Текущая версия схемы 4 (`_MIGRATIONS = [V1..V4]`, `PRAGMA user_version`). **Нет колонки/индекса под `match_key`.**

`Library.copies(artist, title)`: `key = match_key(artist, title)`; `SELECT * FROM library` целиком, затем в Python сравнение `match_key(i.artist, i.title) == key` — полный скан на каждый вызов. Вызывают его три места: `api_songs._copies` (блок «Хранилища» в `details`), `api_jobs.rename` (стр. ~425) и `handlers.RenameHandler._rename_tags` (стр. ~1576).

План под индекс:
- миграция V5: `ALTER TABLE library ADD COLUMN match_key TEXT; UPDATE library SET match_key = karaoke_match_key(artist, title); CREATE INDEX library_match_key ON library(match_key)`. Функцию `karaoke_match_key` зарегистрировать в `connect()` рядом с `karaoke_song_id` (`conn.create_function("karaoke_match_key", 2, lambda a, t: song_tag_key(a, t), deterministic=True)`; хранить строку `naming.song_tag_key(artist, title)` — это `match_key` через `\n`, tuple в SQLite не лечь);
- `_migrate` режет скрипт по `;` (`script.split(";")`), поэтому внутри миграции не должно быть `;` в строках и комментариях;
- `_LIB_COLS = [f.name for f in fields(LibraryItem)]`, `_insert` пишет `_LIB_COLS + ["song_id"]` — добавить `match_key` сюда (значение вычислять из artist/title); `LibraryItem.from_row` делает `d.pop("song_id", None)` — так же вытащить `match_key`, иначе `cls(**d)` упадёт;
- `copies()` заменить на `SELECT * FROM library WHERE match_key=?`;
- `naming.match_key(artist,title)` — tuple из двух свёрток (`strip().casefold().replace("ё","е")` → `safe_name`); `song_tag_key` = они же через `\n`;
- обновить `tests/core/test_db.py` (там есть тест миграции V3→V4; взять за образец) и проверить `tests/api/test_tags.py::test_details_copies_*`.

`GET /api/songs/{id}/details` (`api_songs.get_details`, стр. ~211): `ctx.find_song` → `storage = _song_storage` → `_folder_files` → `ultrastar.parse(_read_txt)`; возвращает `{song: _song_card(...), headers, singers, media{audio,instrumental,vocals,video,cover,background,midi}, files[{name,size,mtime}], copies[{song_id,target_id,target_name,current}], usdb_url}`. `headers` — по `DETAIL_HEADERS` (author, bpm, gap, language, year, genre, edition, creator, videogap). Имена файлов нормализуются `_present(names, value)` (без регистра, без `/`). Запрос зависит от хранилища песни: недоступно → 503.

## 5. Очередь заданий

Таблица `jobs` (V1): `id INTEGER PK AUTOINCREMENT, type, state DEFAULT 'queued', stage, percent, artist, title, song_id, params TEXT DEFAULT '{}', error, cancel_requested, parent_id, created_at, started_at, finished_at`; индекс `jobs_state(state, id)`. Дополнительных колонок (приоритет, `start_at`) нет — понадобится миграция V5/V6 (разрез скрипта по `;`!). `Job` — dataclass с теми же полями, `Job.to_dict()` = `asdict`.

`class Jobs` (стр. ~227):
- `enqueue(type, song_ref, params=None, *, parent_id=None)`; `enqueue_with(type, song_ref, make_params(job_id), *, parent_id=None)` — `INSERT` + вычисление params в одной транзакции (воркер не увидит задание без параметров).
- `claim_next(types=None)`: в одной транзакции `UPDATE jobs SET state='running', started_at=? WHERE id = (SELECT id FROM jobs WHERE state='queued' [AND type IN (...)] AND (json_extract(params,'$.retry_at') IS NULL OR json_extract(params,'$.retry_at') <= ?) ORDER BY id LIMIT 1) RETURNING *`. Порядок только `ORDER BY id`; `now()` — ISO UTC с секундами (`db.now(after_s=0.0)`), сравнение строк. **Это единственная точка выбора следующего задания** — и «ночное расписание», и ручной порядок надо делать здесь: например, `json_extract(params,'$.start_at') <= now` по аналогии с `retry_at` (но `retry_at` уже занят ожиданием хранилища и перезаписывается `wait_retry`, `restart` для copy/rename его снимает — для расписания лучше отдельный ключ `start_at` или колонка) и `ORDER BY priority, id` (новая колонка `sort_key`/`position`).
- `list(limit=50)`: `SELECT * FROM jobs ORDER BY id DESC LIMIT ?` (новые сверху); `active(type)`: `ORDER BY id`; `get`, `update(id, **fields)` (разрешены только поля из `_JOB_UPDATABLE = {"state","stage","percent","artist","title","song_id","params","error","cancel_requested","started_at","finished_at"}` — новое поле надо добавить сюда), `request_cancel`, `fail_interrupted`.
- Перезапуск (`api_jobs.restart`) создаёт НОВОЕ задание с новым `id` (`parent_id` = старое), поэтому порядок по `id` для перезапусканных заданий меняется — это нужно учесть при ручной сортировке.
- Воркер: один процесс, один поток; цикл `_loop` → `_claim` → `run_job`, пауза `poll=1.0` с, если нечего брать. Задания, ожидающие по `retry_at`, возвращаются `state="queued"` с `stage="Ждёт хранилище «X»"` (`handlers.wait_retry`, `COPY_RETRY_S=60`).

API (`web/app/api_jobs.py`): `GET /api/jobs?limit=` (1…1000, по умолчанию 50) → список `Job.to_dict()`; `GET /api/jobs/{id}`; `POST /{id}/cancel` (409, если уже завершено); `POST /{id}/restart` (201, только завершённое); `POST /{id}/republish`; `GET /{id}/log?from=|tail=`, `GET /{id}/log/stream` (SSE). `import_router` подключается ДО `jobs_router` (`web/app/main.py`), иначе `/api/jobs/import` уйдёт в `/{id}`. Для нового `POST /api/jobs/{id}/move`/`/schedule` ставить его так же, учитывая порядок маршрутов, и 409 для не-`queued`.

Фронт очереди — `web/static/js/queue.js` (раздел «Очередь», 263 строки): `mount/show/hide/startPolling`; `poll()` раз в `POLL_MS = 2000` мс (пока вкладка видима) читает `api.jobs(50)` и вызывает `render(jobs)`: карточки `cards: Map(id → {el, parts, job, sig})` создаются один раз (`createCard`) и обновляются (`updateCard`), порядок как в ответе сервера. Кнопки перестраиваются только при смене `sig = state|stage|cancel_requested|logOpen`. Справочники `TYPE_LABEL`, `STATE_LABEL`, `STAGE_LABEL`. Счётчик в меню: `hooks.setQueueCount(jobs.filter(ACTIVE.includes(state)).length)`. Ограничение: только 50 последних, давно поставленное задание из очереди может оказаться за пределами окна — для ручного порядка/расписания либо поднять `limit`, либо отдельный запрос только `queued`. `api.js`: `JOB_ACTIVE`, `JOB_FINAL`, `STAGE_PUBLISH`, `canRepublish(job)`.

## 7. Задание copy, mtime/updated_at, расхождения копий

`Jobs.enqueue_copy(song_ref, *, rel_dir, txt_name, from_target, to_target, replace=False, wait=False, replace_rel_dir=None, after_job=None, parent_id=None)` — единственная сборка params; уже активное такое же (`Jobs.active_copy(rel_dir, from_target, to_target)`) возвращается вместо нового. params: `{rel_dir, txt_name, from_target, to_target, replace, wait, [replace_rel_dir], [after_job]}` + служебные `retry_at`, `wait_logged_at`.

`CopyHandler.run` (handlers.py ~1192): ждёт `after_job`; `download_song_dir(ctx, job, rel_dir, from_target, name)` → `jobs/<id>/in/` (при restart берёт вход родителя; `read_song(rel_dir) is None` → `JobFailed("source", ...)`); `target.exists(rel_dir)`: при `replace=false` пишет «Уже есть… пропущено» и выходит `done`, при `replace=true` — `ctx.trash.move_to_trash(target, rel_dir, reason="заменена копией")`, при сбое откат; `target.upload_dir(in_dir, rel_dir)` (медиа сначала, `.txt` последним, через `.part`); сбой хранилища при `wait=true` → `wait_retry` (обратно `queued`, `retry_at` +60 с); `_index(ctx, job, target, rel_dir, own_id, removed=...)`. Для зеркала: «Ничего не удаляет само» — значит синхронизация = только постановка `copy` для отсутствующих песен (`replace=false`) и, отдельно по явной кнопке, `replace=true` для расходящихся. `POST /api/jobs/copy` (`only_missing=true` по умолчанию) уже реализует «добавить недостающее» по `Library.get(target.id, rel_dir)` (сравнение по `rel_dir`, а не по `match_key`; при другом написании исполнителя копии не найдёт — для зеркала лучше сравнивать по `match_key`).

Что есть для обнаружения расхождения:
- `library.mtime` (REAL) — mtime `.txt` в конкретном хранилище (`Entry.mtime` из `_scandir`); в API — `updated_at`. **Копирование не сохраняет mtime** (`write_atomic` пишет новый файл; в `upload_dir` нет `utime/copystat`), поэтому у только что скопированной копии mtime новее оригинала. Сравнение mtime между копиями ненадёжно как признак «разошлись».
- Надёжнее: размеры файлов папки — `Storage.sizes(rel_dir) -> {путь: байты}` (без чтения содержимого) и, при несовпадении `.txt`, сравнение байт `storage.read(rel)`. Либо хэш `.txt` в новую колонку индекса при сканировании. Список общих файлов: `Storage.listdir(rel_dir)` → `Entry(name,is_dir,size,mtime)`.
- Копии одной песни: `Library.copies(artist, title)` (после п. 3 — по индексу), `api_songs._copies` и `details.copies`.
- Сканирование: `Storage.list_songs(max_depth=4)`, `read_song(rel_dir)` → `SongEntry` (`to_library_item`); `AppContext.rescan(target_id)` фоном по одному, `refresh_song(rel_dir, target_id)` точечно.

## 11. ultrastar.decode (битая кодировка)

`core/karaoke_core/ultrastar.py::decode(data) -> (text, encoding, had_bom)` (стр. 222): BOM UTF-8 → `"utf-8", True`; иначе последовательно строго `utf-8`, строго `cp1251`; иначе `latin-1` (последний рубеж, всегда проходит). Кодировка запоминается в `Song.encoding` (парсер `parse(data)` сохраняет её, `render(song)` пишет обратно в той же; `UnicodeEncodeError` при записи не кодируемого символа — в API это 400 «Символ не поддерживается кодировкой файла (…)»).

Следствия для «проверки кодировки»: отдельного признака «битая» нет. Практические сигналы: (1) `encoding == "latin-1"` — ни utf-8, ни cp1251 не подошли (байт 0x98 в cp1251 не определён); (2) в тексте есть `\ufffd`; (3) mojibake: UTF-8-файл, прочитанный как cp1251, даёт пары вида «Р°», «Рё», «С‚» (после `decode('cp1251')` символы `Р`/`С` и `Ѓ-ё`); эвристика — доля таких пар среди кириллицы либо попытка `text.encode('cp1251').decode('utf-8')` без ошибки и с меньшей долей «странных» символов; (4) cp1251, прочитанный как utf-8, не пройдёт строгий `utf-8` (поэтому корректно определяется), а вот cp866/koi8-r-файл молча «пройдёт» как cp1251 и даст кракозябры в заголовках `#ARTIST/#TITLE` — частично лечится сопоставлением с именем папки (`LibraryItem.rel_dir`). Для проверки библиотеки читать `.txt` через `storage.read` (или `read_song`), затем `ultrastar.decode(data)` — дёшево, без парсинга всех строк.
