# Спецификация: karaoke-services

## Задача

Песни для домашнего караоке (UltraStar Deluxe на Raspberry Pi) приходится генерировать вручную: копировать mp3 на Windows-ПК, вызывать UltraSinger длинной командой с ключами, которые легко забыть, исправлять за MusicBrainz исполнителя и название, чинить нулевые ноты и раскладывать файлы по шаре. С телефона это не сделать совсем. Песни, скачанные с USDB, остаются без минусовки, а ошибку в одном слове готовой песни можно исправить только перегенерацией или ручной правкой .txt.

## Решение

На Windows-ПК постоянно работает сервис из двух контейнеров. Его страница открывается из любого браузера в домашней сети, в том числе с телефона, под общим паролем. На ней можно:

- добавить песню: исполнитель, название, mp3, по желанию текст и обложка, модель Whisper и язык;
- следить за очередью: этап, процент, живой лог; задание можно отменить или перезапустить;
- открыть список всех песен в папке результата (по умолчанию songs-папка UltraStar на Pi), включая скачанные с USDB, и для каждой:
  - удалить в корзину с возможностью восстановить;
  - перегенерировать;
  - сделать минусовку;
  - поправить исходный текст и перегенерировать;
  - поправить слова и строки готовой песни без перегенерации;
- выбрать, куда выкладывать готовые песни: на SMB-шару или в локальную папку.

Готовая песня появляется в `<Исполнитель>/<Исполнитель - Название>/`. В ней `#ARTIST` и `#TITLE` взяты из формы, ноты нулевой длины исправлены, а заголовки `#AUDIO`/`#MP3` указывают на оригинал и `#INSTRUMENTAL` на минусовку, как сейчас.

## Решения по реализации

### §1 Стек и контейнеры

- **web**: Python 3.12, FastAPI + Uvicorn, SQLite (WAL), `smbprotocol` (smbclient), статический фронтенд на чистых HTML, CSS и JS (ES-модули, без сборки). Почему так: один язык с воркером и UltraSinger, нет node-тулчейна, страница лёгкая для телефона.
- **worker**: образ на `nvidia/cuda:12.6.3-cudnn-runtime-ubuntu22.04`, Python 3.12 (deadsnakes), ffmpeg. UltraSinger ставится из `ULTRASINGER_GIT` через `additional_contexts` compose (git URL или путь), его зависимости ставит `uv pip`, затем torch, torchaudio и torchvision 2.8.0/0.23.0 с `https://download.pytorch.org/whl/cu126` и `numpy<2.5`. Почему так: Linux-колёса cu128 собраны без sm_61, а cu126 поддерживает Pascal; Dockerfile UltraSinger не используется, чтобы не править fork ради индекса.
- **Общий пакет `karaoke_core`** ставится в оба образа. В нём БД, модели, хранилища, парсер и писатель UltraStar .txt, постобработка, имена файлов. Почему так: и web, и worker читают одну БД и пишут в одну папку результата.
- **GPU** доступен только worker (`deploy.resources.reservations.devices: nvidia, count 1`). Compose запускается в контексте `desktop-linux`: на этой машине активен Windows-движок, и README даёт команды с `--context desktop-linux`, не меняя контекст по умолчанию.
- **Сеть**: web публикует `${WEB_PORT:-8080}` на все интерфейсы хоста; worker наружу ничего не публикует.

### §2 Взаимодействие web ↔ worker

Общая SQLite в томе `data`. Web ставит задания (`INSERT … state='queued'`). Worker раз в секунду забирает одно задание: `UPDATE jobs SET state='running' … WHERE id=(SELECT id … WHERE state='queued' ORDER BY id LIMIT 1) RETURNING *`. Отмена: web ставит `cancel_requested=1`, worker проверяет флаг каждую секунду. Лог пишется в файл тома, web отдаёт его через SSE (tail). Почему так: на одном ПК очередь на Redis лишняя, а SQLite в именованном томе (ext4 в WSL-VM) надёжна при двух процессах. Bind-mount из NTFS для БД не используется.

Состояния задания (конечный автомат):

```
queued → running → publishing → done
queued → cancelled
running|publishing → failed | cancelled
failed(stage=publish) --«Выложить повторно»--> новое задание type=publish
любое конечное --«Перезапустить»--> новое задание с теми же параметрами
при старте worker: running|publishing → failed("прервано перезапуском")
```

Типы заданий: `generate` (новая песня или перегенерация), `instrumental`, `publish`. Тип — значение из реестра обработчиков, поэтому новые типы («скачать с USDB», «подтянуть LRC») добавляются отдельным обработчиком без правки очереди.

### §3 Том `data` (иерархия Исполнитель/Песня)

```
/data/karaoke.sqlite
/data/songs/<Исполнитель>/<Исполнитель - Название>/
    source/        input.mp3, lyrics.txt, cover.<ext>, params.json   ← для перегенерации
    jobs/<job-id>/ рабочая папка задания: вход, выход UltraSinger, результат постобработки
/data/logs/<job-id>.log
/data/trash/<UTC-время>__<id>/<Исполнитель>/<Исполнитель - Название>/ + meta.json
```

Рабочая папка задания удаляется после успешной выкладки или отмены, после ошибки остаётся (нужна для «Выложить повторно»). Логи хранятся 30 дней. Отладка `lyrics_debug.json` (если включена) копируется в `jobs/<id>/debug/` и в папку результата не попадает.

Том `models` — `/models`: `HF_HOME=/models/huggingface`, `TORCH_HOME=/models/torch`, `XDG_CACHE_HOME=/models/xdg`; каталог словарей pyhyphen перенаправляется в `/models/hyphen`.

### §4 Запуск UltraSinger

Вход копируется в `jobs/<id>/in/<Исполнитель - Название>.mp3`: имя «Исполнитель - Название» нужно UltraSinger и MusicBrainz. Текст — в `jobs/<id>/in/lyrics.txt` (UTF-8). Команда:

```
python /app/UltraSinger/src/UltraSinger.py -i <in.mp3> -o <jobs/id/out>
  --whisper <model> --whisper_compute_type <int8> --whisper_batch_size <4>
  --language <ru> [--whisper_align_model <...>] [--lyrics <lyrics.txt>]
  [--vad_onset x] [--vad_offset y] [--demucs <model>] [--keep_cache]
  --format_version 1.2.0
```

Процесс запускается в отдельной группе процессов, stdout и stderr объединены. Результат — единственная подпапка в `out/`; если подпапок не одна, это ошибка. Перед `--lyrics` текст проходит через `prepare_lyrics(text) -> text`: сейчас это нормализация переводов строк и BOM, а позже здесь будет раскрытие `[Припев]` (R29). Флаг `--interactive` не передаётся никогда.

### §5 Прогресс

Маркеры строк лога (без ANSI) → этап и минимальный процент:

| Маркер | Этап | % |
|---|---|---|
| `Checking GPU support` | Подготовка | 2 |
| `Separating vocals from audio with demucs` | Отделение вокала | 5 |
| `Reduce noise from vocal audio` | Очистка вокала | 25 |
| `Loading whisper with model` | Загрузка модели | 30 |
| `Transcribing` | Распознавание | 35 |
| `Using lyrics from` / `anchored` | Выравнивание текста | 50 |
| `Hyphenate using language code` | Расстановка слогов | 60 |
| `Pitching with SwiftF0` | Определение высоты нот | 65 |
| `Creating UltraStar file` | Запись песни | 80 |
| `Converting audio to mp3` | Минусовка в mp3 | 85 |
| `Creating midi file` | MIDI | 90 |
| (после выхода 0) | Постобработка | 95 |
| (выкладка) | Выкладка | 97→100 |

Внутри этапов процент уточняется по tqdm-строкам (`NN%|`), но не выходит за процент следующего этапа. Процент никогда не уменьшается.

### §6 Постобработка (`karaoke_core.postprocess`)

1. Разобрать .txt (заголовки по порядку + тело).
2. Запомнить `#ARTIST` от MusicBrainz, затем выставить `#ARTIST`/`#TITLE` из формы.
3. Фильтр MusicBrainz (история 26) и обложка из формы.
4. Нулевые ноты: длина 0 → 1. Если следующая нота той же строки начинается раньше нового конца, она и все следующие ноты строки сдвигаются вправо на нужное число битов; разрыв строки `- N` сдвигается, если оказался раньше конца последней ноты. Повторять до отсутствия перекрытий.
5. Переименовать все файлы в `<Исполнитель - Название>` + суффикс (`.mp3`, ` [Instrumental].mp3`, ` [Vocals].mp3`, ` [CO].jpg`, `.mid`, `.txt`) и обновить ссылки в `#MP3`, `#AUDIO`, `#VOCALS`, `#INSTRUMENTAL`, `#COVER`.
6. Записать .txt в UTF-8 без BOM, тело и порядок заголовков сохранить.

### §7 Хранилище (папка результата)

Интерфейс `Storage` (см. «Границы»), реализации `LocalStorage(root)` и `SmbStorage(host, share, base_path, user, password)`.

Бриф допускал два способа: CIFS-монтирование в compose или Windows-диск. Заменяю оба одним SMB-клиентом внутри контейнера:
- CIFS-том задаётся в compose при старте, его нельзя переключить из веба (G01). Монтирование выполняет Docker-демон, и при недоступном Pi контейнер не стартует.
- Сетевой диск Windows (`K:`) Docker Desktop в контейнер не пробрасывает: такие диски видны только в сессии пользователя. Bind-mount UNC-пути тоже не работает.
- Локальный путь Windows всё равно поддерживается: это `LocalStorage` (история 37).

Имя `pi` внутри контейнера не резолвится, поэтому по умолчанию в `.env` стоит адрес, полученный через `pi.local`. Учётка по умолчанию берётся из `.env` (R23). Если цель меняется в вебе, её учётка хранится в томе `data` (G01). Перенос в корзину = скопировать в том → проверить размеры → удалить на шаре. Восстановление — обратный порядок.

### §8 Индекс песен

Таблица `library` (`target_id`, `rel_dir`, `txt_name`, `artist`, `title`, `audio`, `instrumental`, `cover`, `is_duet`, `own_song_id`, `mtime`, `scanned_at`). «Своя» песня — та, у которой есть запись в `songs` (исходники в томе) с тем же `rel_dir`. `song_id` в API для песен из папки — стабильный хэш `target_id + rel_dir`.

### §9 UltraStar .txt (`karaoke_core.ultrastar`)

Парсер читает байты, определяет кодировку (BOM UTF-8 → UTF-8 → cp1251) и запоминает её, BOM и тип перевода строк. Модель: упорядоченные заголовки (включая неизвестные), строки нот (`:`, `*`, `F`, `R`, `G`), разрывы `- N` (и `- N M`), `E`, признаки `P1/P2`, `#RELATIVE`. Писатель воспроизводит файл байт в байт, если модель не менялась (проверяется тестом на круговое преобразование). Точечная вставка заголовка для минусовки работает на уровне строк, без перезаписи модели (история 46). Время бита: `GAP_ms + beat * 60000 / (BPM * 4)`.

### §10 Авторизация

Middleware HTTP Basic: если `WEB_PASSWORD` не пуст, любой запрос без верного пароля получает 401 с `WWW-Authenticate`. Сравнение через `secrets.compare_digest`. Поверх HTTP в домашней сети, без TLS — это осознанно (см. «Вне рамок»).

### §11 Фронтенд

Одна страница с разделами по хэшу: «Очередь» (по умолчанию), «Новая песня», «Песни», «Корзина», «Настройки». Редакторы открываются из карточки песни. Опрос `/api/jobs` каждые 2 с, пока вкладка видна; SSE для лога открытого задания. Тёмная и светлая темы — по `prefers-color-scheme`.
